## 引言

當棕地（brownfield）專案引入規格框架時，一個結構性矛盾立即浮現。規格的語義是「系統應該如何運作」——規範性的（prescriptive）。但棕地專案手上的知識幾乎全部來自逆向工程，記錄的是「系統碰巧如何運作」——描述性的（descriptive）。兩者在文字上可能相似，但權威性質完全不同：一個是契約，另一個是觀察報告。

直接把逆向工程的觀察寫進規格目錄，觀察就獲得了規格的權威地位。形式上它們是「規格」——位於規格目錄中、使用規格格式、被規格工具鏈處理。實質上它們仍然是觀察——沒有人審查過這些行為是否是設計意圖，沒有人確認過它們應該被保留而非修正。

這就是虛假權威（false authority）：形式賦予了權威，但實質不支撐這個權威。

虛假權威不是棕地規格化的特有問題。它以不同的載體反覆出現：失效的治理機制繼續存在製造「治理已到位」的錯覺；測試案例通過被等同於「行為正確」而實際上測試本身可能反映的是錯誤的預期；過期的流程文件繼續被遵循因為「文件說要這樣做」。共同的結構是：某個機制的形式外殼完好，但內容已經不再支撐它所宣稱的權威。

虛假權威比缺乏權威更危險。缺乏規格時，所有人知道規格缺失——這種意識本身激發行動。虛假規格存在時，所有人以為規格已到位——直到某天發現團隊一直在保護一個「規格化的 bug」。誠實地標記知識的性質——即使承認大部分行為尚未被規格化——是比追求形式完整更務實的選擇。

雙層結構正是對虛假權威的設計回應。

## 分析

### 雙層設計的核心原則

雙層結構的核心原則是：**在同一份規格檔案中，用結構位置區分兩種性質不同的知識**。

| 層 | 語義 | 來源 | 語言風格 | 權威等級 |
|---|------|------|---------|---------|
| Architecture | 系統如何運作 | 逆向工程觀察 | 描述性——is / does / has | 事實記錄，可被程式碼推翻 |
| Requirements | 系統應該如何運作 | 審查過的設計意圖 | 規範性——MUST / SHOULD / MAY | 行為契約，程式碼必須遵循 |

兩層共置於同一檔案是刻意的設計選擇，不是偷懶。它們描述的是同一個領域的兩個面向——將它們分成獨立檔案會破壞認知的連續性。讀者理解一個模組時，需要同時看到「它現在做什麼」和「它應該做什麼」，兩者的對照本身就是有價值的資訊。當 Architecture 描述的行為與 Requirements 定義的契約一致時，讀者獲得信心；當兩者存在差距時，讀者知道哪裡需要關注。

兩層的粒度天然不同。Architecture 運作在模組層級——資料流、元件互動、架構模式——提供鳥瞰視角。Requirements 運作在場景層級——Given/When/Then 的具體行為契約——提供街景視角。這種粒度差異是特性而非缺陷：讀者接觸一個模組時，自然的認知路徑是先鳥瞰（理解全景）再街景（理解具體契約）。如果兩層粒度相同，其中一層就是多餘的。

### 畢業機制：從觀察到契約

雙層結構的動態面向是畢業（graduation）——Architecture 條目在什麼條件下升格為 Requirements。

畢業的觸發不應是定期審查。「每月檢視 Architecture 段落決定哪些可以升格」會變成缺乏語境的儀式——脫離具體修改場景的判斷，品質不可靠。更自然的觸發是**實作接觸**：當你因為修改需要而接觸某段行為時，你被迫對它的性質做出判斷。

兩個場景構成自然的畢業觸發點。第一個是差量變更提案。當提案者寫下「將行為 X 從 A 改為 B」時，這個動作隱含地確認了 A 是此前的預期行為——否則修改的性質不是「變更行為」而是「修正錯誤」。提案的動作迫使撰寫者釐清被修改對象的性質，這種釐清就是畢業判斷的自然發生點。第二個是實作前的規格比對。在修改某模組的程式碼之前比對規格，如果發現 Architecture 中描述了一個行為但 Requirements 中沒有對應的場景，開發者需要做出判斷：這個行為是否應該被保留？如果是，寫一個 Requirement 場景來保護它。如果不確定，保留在 Architecture。

畢業的判斷標準是：**能否為該行為寫出一個有意義的 Given/When/Then 場景，並且團隊同意這個場景描述的是「應該發生的事」而非「碰巧發生的事」**。「有意義」意味著場景不是對程式碼的逐行翻譯，而是對行為意圖的表達。「團隊同意」意味著畢業不是個人判斷，而是共識。如果無法滿足其中任何一個條件——行為太模糊無法場景化，或者團隊對「是否應該」沒有共識——條目留在 Architecture，等待更多資訊。

這意味著畢業是漸進的、局部的、由實作需求驅動的。不需要一次性將所有觀察升格為規格——只有被接觸到的區域才需要做出判斷。這與棕地現實相符：你不可能一次性理解整個遺留系統的所有意圖，但你可以在每次修改時，對被修改區域做出明確的判斷。

### 退化防線（degradation safeguard）：防止觀察債務（observation debt）的無限累積

雙層結構的結構性風險是退化：Architecture 持續膨脹（記錄觀察是低成本的），Requirements 始終稀薄（確認意圖是高成本的）。團隊持續「看到什麼記什麼」但永遠不做「這是否是設計意圖」的決定。

在棕地遷移的早期，Architecture 遠大於 Requirements 是正常的過渡狀態。逆向工程產出大量觀察，而意圖確認需要時間和領域知識。比例可能是 9:1 甚至更極端——這不是退化，而是誠實反映知識的成熟度。退化發生在**比例不隨時間收斂**的時候：如果團隊在一段時期內修改了大量程式碼，但每次修改都跳過了畢業判斷，Architecture 和 Requirements 的比例停滯不變，這意味著畢業機制沒有運作。

防線不是比例監控。設定「Architecture 條目佔比不得超過 70%」之類的指標會激勵草率升格——為了改善數字而把觀察包裝成規格，這恰恰是雙層結構試圖避免的虛假權威。

更有效的防線是**將畢業判斷嵌入既有的工作流程節點**。規格比對在實作前自動觸發——如果觸及的區域只有 Architecture 沒有 Requirements，標記這個缺口讓開發者決定。差量變更提案要求明確標示被修改行為的性質——是變更意圖還是修正偶然。程式碼審查時，如果修改涉及的行為只有 Architecture 描述，審查者可以追問。三個節點形成分散式的壓力：每個節點的成本很低——一個判斷、一個標記——但累積效應是 Requirements 隨著實作接觸逐漸充實。

### 永不畢業的條目與粒度啟發式

並非所有 Architecture 條目都是畢業的候選者。有些條目記錄的是純粹的實作細節——「模組 A 透過特定協議與模組 B 通訊」——這不是行為契約，而是架構事實。這類條目的歸宿不是 Requirements，而是持續留在 Architecture 作為架構知識，或者遷出到更適合的位置（例如共置 README）。

區分「待畢業的行為觀察」和「純粹的架構知識」可以用一個粒度啟發式（granularity heuristic）：**如果一個 Architecture 陳述可以被改寫為 Given/When/Then 場景而不損失意義，它是一個未畢業的行為觀察**。如果改寫會扭曲它的本質——因為它描述的是結構而非行為——它是架構知識，永不畢業是正確的歸宿。

這個啟發式也服務於退化防線：當 Architecture 中大量條目通過粒度測試但始終沒有畢業，這是一個更精確的退化信號——比單純的條目數量比例更有診斷價值。

### 雙層與差量模型的交互

當差量變更提案（delta spec）修改的對象只存在於 Architecture 時，一個語義灰區浮現。差量模型的三個語義區段——ADDED、MODIFIED、REMOVED——假設被操作的對象是已確認的行為契約。但 Architecture 中的條目不是契約，而是觀察。

修改一個 Architecture 條目不是「變更已確認的行為」（行為還沒被確認），也不完全是「首次規格化」（確實有東西被改變了）。這個情況需要的語義是：**在觀察的基礎上建立契約**——同時做兩件事：確認原始觀察的意圖性，並修改這個意圖。

實務上的處理方式是：差量提案將這類修改標記為 ADDED（新增 Requirements 條目），同時在提案中註明它取代了哪個 Architecture 條目。這比 MODIFIED 更誠實——因為被修改的不是一個已存在的契約，而是一個觀察正在被首次契約化。MODIFIED 暗示「改變已確認的行為」，ADDED 明確「建立新的行為契約」。

## 反思

### 雙層結構自身的鷹架性質

一個值得追問的問題是：雙層結構本身是基礎設施還是鷹架？

如果棕地專案持續成熟——越來越多行為被確認為意圖、越來越多 Architecture 條目畢業為 Requirements——Architecture 層是否會逐漸清空？如果會，雙層結構最終收斂為單層（全部 Requirements），而 Architecture 層的存在就是過渡性的。

但完全收斂不太可能發生。原因有二。第一，新的逆向工程觀察會持續產出——即使舊的觀察畢業了，對系統其他區域的探索會產生新的 Architecture 條目。第二，前面討論的「永不畢業的架構知識」是持久性的——結構描述不會因為行為被規格化而消失。

更準確的預期是：Architecture 層的組成會隨時間改變——從「待畢業的行為觀察」為主，逐漸轉向「純粹的架構知識」為主。雙層結構不會消失，但 Architecture 層的性質會從「未確認的行為」轉向「已確認的結構」。這意味著雙層結構是基礎設施，但它服務的具體功能會隨棕地遷移的進展而演化。

### 誠實的結構性極限

雙層結構提供了區分觀察與意圖的框架，但它無法強制使用者在框架內做出誠實的判斷。如果團隊在所有畢業判斷節點都系統性地跳過——或者更微妙地，將未經充分審查的觀察直接標記為 Requirements——雙層結構會退化為形式。Architecture 和 Requirements 的區分變成標題差異而非實質差異。

這個極限是結構性的：**任何需要人類判斷的機制，其品質上限取決於使用者的誠實意願**。雙層結構降低了做出誠實判斷的成本（提供了明確的位置和格式），但不消除做出判斷的需要。框架可以讓誠實更容易，但不能讓誠實變成自動的。

## 結論

棕地雙層結構是對虛假權威問題的設計回應。它在同一份規格檔案中用結構位置區分描述性知識（Architecture）和規範性知識（Requirements），讓知識的成熟度可見而非被掩蓋。

四個可遷移的原則：

1. **虛假權威比缺乏權威更危險，因為它消除了行動的動機。** 缺乏規格激發「我們需要規格」的意識；虛假規格製造「規格已到位」的錯覺。任何將形式與實質混為一談的做法——把觀察寫成規格、把過期的治理當作有效的保護、把通過測試等同於行為正確——都是虛假權威的變體。辨識形式與實質的落差，是建立真實權威的前提。

2. **畢業是實作驅動的，不是審計驅動的。** 脫離具體修改語境的批量審查會變成儀式。有效的畢業機制嵌入在既有工作流程中——每次觸及某段行為時做出判斷，而非定期掃描全部條目。漸進的、局部的判斷比全面的、定期的審計更符合棕地現實。

3. **粒度差異是設計特性，前提是讀者理解不同層的閱讀目的。** 鳥瞰層（架構概述）和街景層（行為場景）服務不同的認知需求。強制兩層使用相同粒度——要麼把架構寫成場景、要麼把場景寫成概述——都會損害各自的表達力。允許粒度差異，同時用啟發式（「能否改寫為場景」）辨識錯位的條目。

4. **結構可以讓誠實更容易，但不能讓誠實變成自動的。** 雙層結構降低了做出「這是觀察還是意圖」判斷的門檻——提供了明確的位置、格式、和觸發點。但判斷本身仍然需要人的參與和誠實。這是所有需要人類判斷的機制共享的結構性極限，承認它比假裝框架可以自動解決更務實。
