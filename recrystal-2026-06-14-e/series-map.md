# 規格驅動開發與棕地治理：系列地圖

## 系列邊界

本系列處理的是棕地專案如何導入規格驅動開發，而不把規格變成瀑布、幻覺或虛假權威。它的核心問題不是「要不要寫規格」，而是：當系統已有大量未被規格化的歷史行為時，什麼可以被視為契約，什麼只能被視為觀察，什麼必須交給確定性工具執行，什麼仍需要人判斷。

核心問題鏈如下：

```mermaid
flowchart LR
    A[棕地現況<br/>程式碼先於規格存在] --> B[規格債<br/>行為已存在但正確性未被定義]
    B --> C[觀察與意圖混淆]
    C --> D[虛假權威與前瞻性漂移]
    D --> E[雙層結構<br/>觀察性 schema + 約束性規格]
    E --> F[確定性契約<br/>script / linter / CI gate]
    F --> G[閉環觀測<br/>漂移偵測與治理調整]
```

本系列的邊界是 OpenSpec / SDD 的棕地採納、規格稀疏期、規格債、觀察性 schema、約束性規格、差量流程、確定性信任邊界、衝突封存與治理回饋迴路。它不處理一般 AI 信任問題，不展開整體知識架構，不討論術語可逆投影，也不把 Linux / sandbox 權限模型納入；這些應在其他系列各自自含展開。

## 概念槽位與角色

本系列最後形成一篇主報告，因為所有材料都服務同一個核心問題：棕地規格化的難點不是缺少格式，而是權威成熟度不同的知識被放進同一個規格外殼。OpenSpec、SDD 迷思、觀察性 schema、確定性邊界、archive 與 feedback loop 不是平行題目，而是同一條治理鏈的不同階段。

| 槽位 | 核心功能 | 決策 |
| :--- | :--- | :--- |
| 棕地起點 | 說明現有程式碼先於規格存在，規格覆蓋稀疏是正常狀態。 | 保留為主報告背景，避免把 SDD 誤解為先寫完規格再開發。 |
| 規格債 | 將「已實作但未被定義的行為」視為可管理風險，而非必須一次清零的缺陷。 | 保留為核心概念，連接技術債、觀察債務與驗證風險。 |
| 雙層結構 | 區分描述現況的觀察層與定義意圖的契約層。 | 保留為主報告主軸，補入概念地圖。 |
| 選擇性採納 | 說明外部框架可採納思維模型，不必全盤採用工具鏈。 | 保留為採納原則，不拆成 OpenSpec 導入專文。 |
| 確定性邊界 | 說明 LLM 可判斷意圖，但高確定性操作必須交給 script / linter / CI gate。 | 保留為主報告的工程防線，並就地重述「確定性邊界 vs 統計執行層」。 |
| 耦合衝突與封存 | 說明 code-spec 耦合後，回滾會變成新衝突，archive 只解決溯源不解決 reconciliation。 | 保留為閉環治理的反例與邊界。 |
| 回饋迴路 | 說明治理不是設完規則就結束，而要觀測遵守率、有效性與摩擦成本。 | 保留為結論段落，作為整個系列的運營閉環。 |

## 合併、移出與保留決策

本系列只需要一篇主報告。拆成「OpenSpec 採納」「觀察性 schema」「確定性邊界」三篇會讓讀者誤以為這些是可獨立套用的工具技巧；單篇主報告更能呈現它們的因果關係：沒有棕地起點，就無法理解規格債；沒有規格債，就無法理解觀察性 schema；沒有觀察與契約的邊界，就無法理解為什麼高確定性操作必須移出 LLM；沒有觀測，就無法知道邊界是否仍然有效。

本次保留為主報告內部分工段落的子題：

- OpenSpec / SDD 的規格即契約、差量模型與結構即語意。
- 鷹架辨識與選擇性採納，作為外部框架整合時避免權威互斥的原則。
- 棕地雙層結構，作為觀察與意圖的主要分界。
- 規格稀疏期與規格債，作為非瀑布導入的基礎模型。
- 觀察性 schema，作為收容現況、衝突與願景降級的結構化資產。
- 命名與 schema 的物理邊界，作為避免純文件漂移的工程條件。
- 確定性信任邊界、耦合衝突、archive 與 feedback loop，作為規格治理進入運營期後的閉環模型。

移出本系列的部分不是刪除，而是因為它們回答不同層級的治理問題：

| 去向 | 移出理由 |
| :--- | :--- |
| 信任邊界與驗證瓶頸 | 自洽、可信、外部裁決與驗證容量是更一般的 AI 協作信任問題；本系列只處理規格治理中的確定性契約。 |
| AI 協作治理與知識架構 | 權威入口、知識路由與 AGENTS.md 屬於治理知識分層；本系列只保留規格資料在棕地中的權威成熟度。 |
| 架構約束與決定性管線 | SSOT、多維資料治理與 pipeline gate 可獨立展開；本系列只用到確定性 gate 作為規格信任邊界。 |
| 術語治理與可逆投影 | 命名污染、穩定鍵與術語生命週期另有完整治理模型；本系列只處理命名進入 schema / linter 後的物理約束。 |
| 人機協作與能力培育 | 團隊如何學會使用 AI、何時不用 AI、人才培育與手寫代碼價值不在本系列範圍。 |
